# Interactive Chats

## Status

Approved. Implements [issue #164](https://github.com/lacedon/Automator/issues/164). The issue's original wording ("make chats into follow-up chats with immediate transcript and timers") was reframed during design review: today's Chats become **Follow-up mode**, and a new **Interactive mode** exposes what a provider's interactive chat can do (open questions, timers, live output).

## Intent

Let a user start a Chat that behaves like the provider's own interactive session: the agent streams its output live, can ask the user open questions mid-turn, and can schedule itself to continue later. Keep today's one-shot Chats unchanged as the default, keep Automation Runs unchanged, and keep the existing Run-based Chat UI (lists, left menu, Run pages, branching, close, cleanup, recovery) working for both modes.

## Decisions

| Area                    | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Chat mode               | A Chat has a **Chat mode** chosen in the new-chat form: **Follow-up mode** (default; today's behaviour — headless one-shot Run per message, resuming the provider session by id) or **Interactive mode** (a long-lived provider session). The mode is fixed for the Chat's life. A branch creates a new Chat in the same mode.                                                                                                                                                                                                                                                         |
| Automations             | Automation Runs are unchanged and are not Chats. They are always headless (Follow-up-style).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| Provider support        | Each launcher declares an interactive capability. Interactive mode is disabled (with an explanatory tooltip) for providers that cannot support it. No degraded fallback.                                                                                                                                                                                                                                                                                                                                                                                                               |
| Live transcript         | Applies to **both** Chat modes (and, as a side effect, Automation Runs): every launcher writes `transcript.md` incrementally while the process runs. Copilot's stdout must be parsed for this, because `--share` writes only on exit. The Chat page picks up progress through the existing `AutoRefresh` polling; no SSE.                                                                                                                                                                                                                                                              |
| Chat bubble             | The agent bubble shows the turn's transcript text inline as plain text (ChatPane's "no HTML, no Markdown" rule stands). The Transcript file link remains. Markdown rendering is out of scope.                                                                                                                                                                                                                                                                                                                                                                                          |
| Protocol                | Common driver over the Agent Client Protocol (ACP): Copilot (`copilot --acp`, native, preview), OpenCode (`opencode acp`, native), Claude Code (`@agentclientprotocol/claude-agent-acp` adapter), Codex (`@agentclientprotocol/codex-acp` adapter). pi uses a native driver over `pi --mode rpc`.                                                                                                                                                                                                                                                                                      |
| Process lifetime        | One long-lived provider process per Interactive Chat. It stays alive between turns until the Chat is closed or it has been idle longer than a configurable idle timeout.                                                                                                                                                                                                                                                                                                                                                                                                               |
| Isolation               | Interactive Chats always work in a per-**Chat** copy of the Repository folder (same copy mechanism as `runs.isolation: "copy"`), regardless of the Repository's isolation setting. Chat copies live in a separate Data Dir folder, `chat-workspaces/<sessionId>/`, which survives restart (startup recovery clears per-Run `workspaces/` only). The copy is created on the first turn, reused by every turn and by the live process, and deleted when the Chat is closed. At worker start, `chat-workspaces/` entries whose session is closed, close-requested or missing are removed. |
| Close chat              | Interactive Chats get a new **Close chat** action (available when no turn is queued or running). The existing per-Run close (`closeRun`/`canClose`) is unchanged for both modes. A closed Interactive Chat accepts no replies but can still be branched.                                                                                                                                                                                                                                                                                                                               |
| Branching               | Branching an Interactive Chat creates a new Chat session with a fresh provider session and a fresh copy taken from the Repository folder; the original Chat's uncommitted work is not carried over.                                                                                                                                                                                                                                                                                                                                                                                    |
| Entry points            | Mode selection is dashboard-only. The ad-hoc CLI (`automator run`) and HTTP API (`POST /api/runs`) keep creating Follow-up Chats.                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| Close with work         | Closing an Interactive Chat whose copy has uncommitted changes or unpushed commits shows a warning and requires confirmation before the copy is deleted.                                                                                                                                                                                                                                                                                                                                                                                                                               |
| Concurrency             | A live session occupies its Repository's `runs.maxConcurrent` slot only while a turn is running. Idle live sessions count against a new global `runs.maxInteractiveSessions` (default 3, Project-overridable); when exceeded, the least-recently-used idle session's process is stopped (it resumes by session id on its next turn).                                                                                                                                                                                                                                                   |
| Restart recovery        | Processes start lazily: after a server restart, a session's process is (re)started only when its next turn arrives, resuming by session id. A turn that was mid-run is marked interrupted, as today. Pending timers (in SQLite) still fire; pending questions keep "Waiting for you".                                                                                                                                                                                                                                                                                                  |
| Permissions             | Interactive mode keeps the current non-interactive tool policy (`allowAll`, allowed tools, `runs.denyTools`). Provider tool-permission requests are answered by that policy, never surfaced to the user.                                                                                                                                                                                                                                                                                                                                                                               |
| Questions               | Both sources: Automator's own `ask_user` tool and each provider's native mechanism (Claude `AskUserQuestion`, Codex `requestUserInput`, ACP elicitation, pi extension UI dialogs).                                                                                                                                                                                                                                                                                                                                                                                                     |
| Question wait           | On a question the Chat session enters **Waiting for you**, shows the question inline (choice buttons when options are provided, free text otherwise) and keeps the tool/request pending for `runs.questionWaitMs` (default 10 minutes, Project-overridable, editable in Settings → Runs). An answer in time resolves the pending request in the same turn. On timeout Automator replies "No answer yet. Stop and wait for the user", the turn ends, the Chat keeps Waiting for you, and the user's eventual answer starts the next turn.                                               |
| Timers                  | Both sources: Automator's `schedule_wakeup` tool and provider-native timers (Claude `/loop`, `CronCreate`, `ScheduleWakeup`). The prompt tells the agent to prefer `schedule_wakeup`; the Chat UI states that native timers are lost if the session process stops.                                                                                                                                                                                                                                                                                                                     |
| `schedule_wakeup` rules | Accepts a delay or absolute time plus a message. One pending Automator timer per Chat (a new one replaces the old); minimum delay 1 minute; firing respects the Repository's effective working hours; cancelled when the Chat is closed. Pending timers are listed in the Chat with a Cancel action.                                                                                                                                                                                                                                                                                   |
| Notifications           | No Teams notification for Waiting for you in this work.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| Delivery                | Five PRs, in order (see below).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |

## Data model

Each **turn** of an Interactive Chat is a Run (Model A). This keeps the Chat chain (`parent_run_id`), Chats list, left-menu status, `/runs/[id]` pages, file route and `canReadRun`, branching, `closeRun`, cleanup, recovery and `interrupted` marking working for both modes.

- New `chat_sessions` table, one row per Interactive Chat: mode, provider, model, provider session id, process id/handle state, copy path, last activity, pending question (text, options, source, request id, asked at), pending Automator timer (fire at, message), closed at. Every Run in an Interactive Chat references it. Follow-up Chats need no row (or a row with mode `follow-up` — the plan decides; Follow-up behaviour must not change).
- `runs.trigger` gains `answer` (user answered a question), `timer` (Automator timer fired) and `agent` (an unprompted native turn, e.g. a Claude `/loop` firing). User messages keep `adhoc`. An unprompted native turn creates its Run when Automator observes the turn starting.
- Interactive turns do **not** ask for or read the agent-written result file (`copilot-result.json`). Automator still writes its own `result.json` for every turn, so the Run page, file route and API behave the same in both modes. The Run summary is the agent's last message in that turn; the outcome is a new `done` value, shown in the UI as **Replied** (distinct from the closed "Done" pill), or the error/interrupted state when the turn fails. Follow-up mode keeps the result-file contract unchanged.
- **Waiting for you** is a Chat-session state, not a Run outcome. During the question wait the Run stays `running`; after the wait it finishes as `done` while the session keeps the pending question. It is distinct from the Automation **Needs you** state and does not affect `canClose`.

## Driver architecture

Today's `ProviderLauncher.start(options)` is one-shot: one prompt in, a process handle out, output parsed after exit. Interactive mode adds a separate session driver contract (alongside, not replacing, the launcher):

- duplex handle: start/resume session, `send(message)`, `respond(requestId, answer)`, `stop()`;
- event stream: text deltas, tool calls, turn start/end (including unprompted turns), questions, permission requests, errors, exit;
- turn completion means "agent idle/settled", not process exit;
- transcript appended to the current turn's `transcript.md` as events arrive.

Drivers: one shared ACP driver (Copilot, OpenCode, Claude adapter, Codex adapter) plus a pi RPC driver. A session manager owns live processes, idle timeout, `maxInteractiveSessions` eviction, per-Chat copies, lazy restart, and routing turns (user message, answer, timer, native unprompted turn) to Runs. Automator's `ask_user` and `schedule_wakeup` are exposed to agents as an MCP server provided by Automator.

## Glossary and ADR

- `GLOSSARY.md`: add **Chat mode**, **Follow-up mode**, **Interactive mode**, **Chat session**, **Waiting for you** (Chat state, distinct from Needs you); update **Chat** to cover both modes and per-turn Runs; keep **Follow-up run** as defined.
- New ADR: interactive provider sessions — long-lived per-Chat processes in per-Chat copies, ACP as the common protocol with a pi RPC driver, Automator-owned questions/timers alongside native ones. It amends ADR 0001 for Interactive Chats (they never use the shared checkout).

## Delivery plan

1. **Live transcript and inline bubbles.** All five launchers write `transcript.md` incrementally (Copilot via stdout parsing); per-run transcript text exposed to the thread read model; ChatPane renders it inline as plain text and keeps refreshing while a run is active. Works for Follow-up Chats and Automation Runs without changing their lifecycle.
2. **Chat mode.** Migration for the mode on Chats/`chat_sessions`; mode selector in the new-chat form (Follow-up default, Interactive disabled per provider capability with tooltip); branching inherits mode; glossary and ADR. Interactive Chats can be created but not yet executed beyond what PR 3 adds (hide/disable until PR 3 if needed).
3. **Interactive runtime.** Session driver contract; ACP driver for Copilot, OpenCode, Claude and Codex adapters; pi RPC driver; session manager (lifetime, idle timeout, `runs.maxInteractiveSessions`, lazy restart, recovery); per-Chat copy and close-with-work warning; turn-as-Run executor path without `result.json`; `trigger` values; tool policy enforcement; capability flags set from a provider spike.
4. **Questions.** Automator MCP `ask_user`; native question mapping per driver; Waiting for you state in session, left menu and Chats list; inline question UI with choices/free text; `runs.questionWaitMs` with timeout reply and next-turn answer (`trigger = answer`).
5. **Timers.** Automator MCP `schedule_wakeup` with its rules; scheduler firing into the queue (`trigger = timer`) respecting working hours; pending timer listing and cancel; cancellation on close; native timer passthrough with unprompted turns (`trigger = agent`); prompt guidance and UI warning about native timer loss.

## Acceptance and tests

- Follow-up Chats and Automation Runs behave as before, except that the transcript is now streamed and shown inline.
- A Chat can be created in either mode; Interactive is unavailable for unsupported providers; mode is fixed and inherited on branch.
- Transcript text appears in the Chat while a turn is running, for every provider.
- An Interactive Chat keeps one process and one copy across turns; idle timeout and `maxInteractiveSessions` eviction stop processes that later resume by session id; restart recovery is lazy and marks mid-run turns interrupted.
- Closing an Interactive Chat with uncommitted/unpushed work requires confirmation; the copy is deleted on close.
- Questions from `ask_user` and native mechanisms show Waiting for you; answers within `runs.questionWaitMs` resolve in-turn; later answers start a new `answer` turn.
- `schedule_wakeup` enforces one timer, 1-minute minimum and working hours, survives restart, is cancellable from the UI and on close; native unprompted turns appear as `agent` Runs.
- Each driver has fake-process tests (protocol framing, streaming, questions, permissions denied by policy, session resume, crash). Run focused tests per PR, then `npm run check`. Live provider smoke checks are documented, not run in CI.
